# tera-tsugu-lab 仕様書

> ステータス: v0.3（壁打ち中。檀家ポータルとスタッフのカレンダーを追加）
> 各モジュールは「決定事項」と「未決事項」に分けて管理する。決定の経緯は §13 の決定ログを参照。

## 0. 構想（ビジョン）

お寺の業務を支援する Web アプリケーション。一般的な「お檀家さん管理」に加えて、次を提供する。

- **MCP 対応**: 住職が自然言語で業務を照会・操作できる
- **今を生きる人への対応**: 故人の情報だけでなく、行事の参加確認やアンケートを行う（Google フォームのような機能）
- **設備管理**: 本堂での法要、結婚式の前撮り、お茶会の場所貸しなど
- **メンタルケアツールのフレームワーク**: お坊さん自身が Claude Code を使い、相談に来る人向けのツールを作れる基盤。データは本人のものとし、本人が希望した場合のみお寺も閲覧できる

## 1. 前提・全体方針

### 決定事項
- **開発の文脈**: ハッカソンで開発する（期間は 11/2〜11/10）。動画撮影があるため、**11/8〜11/9 に完成**させる
- **評価の観点**: 「何ができたか」が問われる。**モックは見せない。デモに出すものはすべて実際に動かす**
- **体制**: 実装は 1 人＋Claude。チームメンバーの日蓮宗の住職が、ドメインの監修とデモ出演を担当する
- **対象規模**: まず 1 つのお寺で運用する。将来は複数寺院に展開できるように、全テーブルに `temple_id` を持たせる
- **デモの主役**: 住職が Claude Desktop から、MCP 経由で自然言語で業務を進める場面
- **利用者**（ハッカソン版での入口）

  | 利用者 | 入口 | 認証 |
  |---|---|---|
  | スタッフ（住職、副住職、執事長、奥様、寺務員、アルバイトなど） | 管理画面、MCP | メールとパスワード。業務の権限は全員同じ。ただし私的な予定の内容は本人しか見られない |
  | 檀家・施主（世帯代表） | 檀家ポータル | 招待コードで登録し、以降はメールのマジックリンクでログイン（§2.2） |
  | 檀家・家族 | 檀家ポータル | 同上 |
  | 檀家でない人（外部の利用者、行事への一般参加者） | 施設予約の申請、公開アンケート | ログインなし（申請番号で状況を確認する） |
  | 相談者（上のどの立場の人でもなりうる） | ケアのポータル | 匿名。端末に保存した ID で識別する |

  - 利用者ごとに何ができるかは、[docs/roles.md](roles.md) にまとめる

### 技術スタック（確定）
| 層 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | Web と MCP サーバーを 1 つの言語で統一できる。お坊さんが Claude Code で拡張するときにも扱いやすい |
| Web | Next.js（App Router）＋ Tailwind | 管理画面、公開画面、ケアのポータルを 1 つのアプリで作れる |
| DB | PostgreSQL（docker compose） | 本番で RLS（行レベルセキュリティ）によるテナント分離ができる |
| ORM | Drizzle | 型安全に扱え、SQL に近い書き方ができる |
| MCP | `@modelcontextprotocol/sdk`（stdio） | Web と同じドメイン層（`src/domain`）を呼び出す |
| 暗号化 | アプリ層で AES-256-GCM（鍵は環境変数） | ケアのデータの本文を暗号化して保存する |
| ホスティング | ハッカソン中はローカル。本番は国内クラウドに限定する | 要配慮個人情報を扱うため、データを国内に置く |

## 2. 檀家管理コア

### 決定事項
- **台帳の単位**: 世帯（家）と個人の 2 層にする。施主の交代や分家は、世帯への所属履歴で表す
- **一般コンタクト**: 檀家ではない外部の人（前撮りの申込者など）は `contacts` として、台帳とは分けて持つ
- **過去帳の項目**: 法号、俗名、没年月日、享年（行年）、続柄、所属する世帯、備考
- **宗派**: 初期設定は日蓮宗。用語と年忌の種類は、宗派ごとのプリセット（設定）で切り替えられるようにする
  - 日蓮宗プリセット: 戒名を「法号」と表記する。年忌は一周忌、三回忌、七回忌、十三回忌、十七回忌、二十三回忌、二十七回忌、三十三回忌、（三十七回忌）、五十回忌 ※**住職に確認する**
- **年忌の計算**: 一周忌は没年の翌年。n 回忌（n≥3）は没年 + (n−1) 年。祥月命日は没した月日とする
- **対応記録**（`contact_logs`）: 案内した、電話を受けた、などを世帯にひもづけて残す

### 未決事項（ハッカソン後）
- 墓地・納骨堂の区画管理、護持会費・お布施・寄付の記録、既存の名簿（Excel）の取り込み

## 2.2 檀家ポータル

### 決定事項
- 檀家がログインして使うポータルを設ける。檀家の立場は 2 つ
  - **施主（世帯代表）**: 世帯の `head_person_id` に設定されている人。家を代表する
  - **家族**: その世帯に属する、施主以外の人（ポータルのアカウントを持つ人）
- **施主ができること**
  - 家全体の法要の予定を見る（確定した法要の予定と、今後の年忌の目安。例: 「2027 年 父・太郎 七回忌」）
  - 家系図を見る（過去帳の故人と、生きている家族を含む）
  - 家を代表して、法要の申し込みをフォームからする（§3.2）
  - 行事への申し込み
- **家族ができること**
  - 行事（花まつり、お会式など）への申し込み
- 用語: 法要を主催する人は一般に「施主」と呼ぶ。世帯の代表を何と呼ぶか（施主、世帯主、檀家代表など）は住職に確認する（§12）
- **家系図**: 続柄（施主から見た関係）だけでは木の形を作れないため、個人どうしの親子関係と配偶者関係を持たせる（`person_relations`）

- **ログイン**: パスワードは使わない
  - 最初の登録: お寺が個人ごとに発行する招待コード（寺報や手紙に QR コードで印刷する）を使う。招待コードは、台帳の個人（`persons`）にひもづいている
  - 2 回目以降: メールアドレスを入力すると、ログイン用のリンク（有効期限は 15 分、1 回だけ使える）が届く
  - ハッカソン中はメールを送らず、開発用の画面にリンクを表示する
  - ログインの状態は 30 日間保つ（高齢の方が何度もログインしなくて済むように）
- **家族の権限は施主が与える**: 施主はポータルで、家族ごとに次の 2 つを設定できる（初期値はどちらもオフ）
  - `can_view_household`: 家系図と家の法要の予定を見られる
  - `can_apply_memorial`: 施主の代わりに法要を申し込める（代理）。申し込みには「誰が申し込んだか」を記録する
- 施主が交代したときは、新しい施主に施主の権限が移る。家族に与えた権限はそのまま残す
- **ハッカソンの実装範囲に入れる**（§10、台本は §11 の場面 7）

### 未決事項
- 檀家が自分で連絡先を直せるか（スタッフの確認を挟むか）
- 施主がまだポータルに登録していないときに、家族の権限をスタッフが代わりに設定できるか

## 3. 年忌法要の受付

### 決定事項
- **年忌の検証**（`verify_memorial`）で行うチェック:
  1. **故人の取り違え**: 名前・世帯・続柄で候補を検索する。候補が複数あれば、法号と没年を並べて確認を求める（自動で 1 人に決めない）
  2. **回忌と年の対応**: 希望された年が何回忌にあたるかを計算し、依頼された回忌と食い違えば指摘する
  3. **命日より後の日ではないか**: 希望日がその年の祥月命日より後なら警告する（法要は命日より前に繰り上げるのが一般的なため）
  4. **併修の提案**: 同じ世帯に、同じ年に年忌を迎える故人がほかにいれば、あわせて営むことを提案する（日蓮宗での呼び方は住職に確認する）
- **担当者**: 法要を担当する人の予定は、スタッフのカレンダー（§3.1）で管理する
- **時間の押さえ方**:
  - お寺で行う場合: 本堂を「法要の時間＋前後のバッファ（初期値 30 分ずつ）」で押さえる。担当者の予定も同じ時間で押さえる
  - 自宅や墓前で行う場合: 本堂は押さえない。担当者の予定を、移動時間（初期値 片道 30 分）を足して押さえる
  - 法要の長さ（初期値 60 分）、バッファ、移動時間は設定で変えられる
- **候補の出し方**（`find_memorial_slots`）: 希望の期間の中から、担当者が空いていて、かつ本堂（お寺で行う場合）が空いている時間帯を列挙する。命日より前の日を優先して並べる。候補にする時間帯は設定で決める（例: 9:00〜16:00 の 1 時間刻み）
- **登録**（`book_memorial_service`）: 法要の予定、担当者の予定、施設の予約を、1 つのトランザクションでまとめて登録する

## 3.2 法要の申し込み（檀家ポータルから）

### 決定事項
- 施主は、ポータルのフォームから法要を申し込める。入力項目:
  - 対象の故人（自分の家の過去帳から選ぶ。複数を選べば併修）
  - 回忌（選んだ故人と希望の年から自動で提案する。手で直すこともできる）
  - 希望の時期（第 1〜第 3 希望）
  - 場所（お寺 / 自宅 / 墓前）
  - 参列の人数、お斎の有無、連絡事項
- 申し込みは `memorial_requests` として受け付ける（状態: `requested` → `scheduled` / `declined`）。この時点では日時は確定しない
- スタッフは管理画面または MCP で申し込みを確認する。年忌の検証（§3）と候補の日時の算出を行い、`book_memorial_service` で日時を確定させる。確定すると、申し込みは `scheduled` になり、施主のポータルの法要の予定に表示される
- 電話で受けた申し込みも、スタッフが同じ `memorial_requests` に登録できる（受付の窓口を 1 つにまとめる）

## 3.1 スタッフのカレンダー

### 決定事項
- お寺で働く人すべて（住職、副住職、執事長、奥様（寺庭婦人）、寺務員、アルバイトなど）の予定を 1 つのカレンダーで管理する
- 法要の担当者になれるのは、`is_officiant` が立っている人だけ。法要の空き判定（§3）では、この人たちだけを対象にする
- **予定は 2 種類**

  | 種類 | 他のスタッフに見えるもの | 内容を見られる人 | 例 |
  |---|---|---|---|
  | `private`（私的な予定） | 時間と「予定あり」だけ | **本人だけ**（管理画面でも MCP でも同じ） | 通院、家族の用事 |
  | `shared`（業務の予定） | 時間、担当者（複数可）、内容のすべて | スタッフ全員 | 法要、行事、施設の立ち会い、外出、勤務（シフト） |
- 私的な予定も、空き判定では「埋まっている時間」として扱う
- 業務の予定には担当者を複数割り当てられる。割り当てられた人それぞれの予定として表示し、空き判定にも反映する
- 法要を確定すると（§3）、担当者を割り当てた業務の予定が自動で作られる
- 私的な予定を入れるには本人のアカウントが必要。ログインしない人の業務の予定は、他のスタッフが代わりに入れられる
- 私的な予定の内容は、ドメイン層で「閲覧者が本人であるとき」以外は返さない（API や MCP の表示側に頼らない）

### 未決事項
- 表示の形式（スタッフごとの横並び、日 / 週 / 月）
- アルバイトのシフトに特別な機能（勤務時間の集計など）が必要か

## 4. MCP 連携

### 決定事項
- **クライアント**: Claude Desktop（ローカルの stdio）。MCP サーバーは管理者として動き、操作した人として設定の `MCP_ACTOR` を記録する
- **権限**: 読み取りは自由。書き込みは確認付き。削除は MCP では行えない
- **確認付きの書き込み（2 段階方式）**:
  1. 書き込み系のツールは、実行せずに **プレビュー（何が登録されるか）と `confirmation_id`** を返す（有効期限は 10 分）
  2. 住職が会話の中で了承すると、Claude が `confirm_action(confirmation_id)` を呼び、はじめて実行される
  - Claude Desktop 自身のツール実行の許可ダイアログとは別に、**業務として内容を確認する**ステップになる
- **監査ログ**: MCP のすべての呼び出し（ツール名、引数の要約、結果、実行者）を `audit_logs` に残す
- **私的な予定**: MCP の操作者（`MCP_ACTOR`）本人の私的な予定だけ、内容まで返す。他人の私的な予定は時間だけを返す
- **メンタルケアのデータは対象外**: ケア関連のテーブルを読むツールは作らない。ドメイン層でも、MCP のコンテキストからのアクセスを拒否する

## 5. 行事・アンケートフォーム

### 決定事項
- **公開範囲はフォームごとに 3 つから選ぶ**

  | モード | 回答の入口 | 入力項目 |
  |---|---|---|
  | `public` | 共通リンク | すべての項目（氏名、連絡先なども入力してもらう） |
  | `members` | 世帯ごとの個別リンク（トークン付き。QR コードにして寺報に印刷することも想定） | **簡易版**: 台帳でわかる項目は聞かない。回答は自動で世帯にひもづく |
  | `both` | 共通リンクと個別リンクの両方 | 個別リンクから来た人は簡易版、共通リンクから来た人は全項目版 |
- 設問ごとに `profile_field`（台帳で補完できる項目）フラグを持たせる。個別リンクから来た場合は、その設問を表示しない
- **設問の種類**（ハッカソン版）: 単一選択、複数選択、短い記述、長い記述、数値（人数）
- **集計**: 選択肢ごとの件数、数値の合計（参加人数）。それぞれ「檀家」「一般」「合計」で出す。CSV で出力できる
- 管理画面でフォームの作成・編集ができる。MCP の `create_form` からも作れる

### 未決事項（ハッカソン後）
- 配信手段（メール / LINE）、日付の設問、回答期限、テンプレート

## 6. 施設予約

### 決定事項
- **施設**（シード）: 本堂、客殿、茶室、境内（撮影用）
- **予約の種類**: 法要、前撮り撮影、茶会、その他
- **予約の状態**: `pending`（申請中＝仮押さえ）→ `confirmed`（確定）/ `rejected`（お断り）/ `cancelled`（取り消し）
- **外部の人からの予約**: ログインせずに申請フォームから申請する → 申請した時点で仮押さえになる → 住職が承認すると確定する。申請番号で状況を確認できる
- **重複チェック**: 同じ施設で、`pending` と `confirmed` の予約は重ねられない。法要（お寺で行うもの）も施設の予約として同じ表で判定する
- 申請中の予約と重なる日時に法要を入れたいときは、警告を出したうえで、住職が調整できるようにする（法要を優先できるように）
- **カレンダー**: 管理画面で、施設ごとの週表示と月表示を出す

### 未決事項（ハッカソン後）
- 料金表と請求、オンライン決済、利用規約への同意、メールでの通知

## 7. メンタルケアツール基盤（フレームワーク）

### 決定事項（必須要件・法令配慮）
- メンタルケアのデータは、健康に関する情報として **要配慮個人情報** にあたる前提で設計する
- データは相談者本人のもの。お寺が閲覧できるのは **本人がツール単位で共有に同意した場合だけ**。いつでも撤回でき、撤回するとすぐにお寺側から見えなくなる。同意と撤回の履歴はすべて残す
- 本文は暗号化して保存する。お寺側の閲覧はすべて監査ログに残す
- **MCP / LLM からは一切参照しない**
- ツールは診断・治療を行わない。そのことを画面に明示する
- **危機兆候の検知**: サーバー側のキーワードルールで判定する（外部の AI には送らない）
  - 検知したら、相談者本人には**必ず**相談窓口（いのちの電話、よりそいホットラインなど）を表示する
  - そのツールで共有に同意している相談者に限り、管理画面にアラートを出す。匿名で共有していない人の場合は、窓口の案内だけにする
- **匿名で利用できる**: ニックネームだけで始められる。ID はランダムに生成して、端末（Cookie）に保存するだけにする。端末を変えると記録には戻れないことを、利用開始時に明示する

### 決定事項（プラグイン方式）
- プラグインは `tools/<tool-id>/` に置く。ビルド時に一覧を自動で生成し、ケアのポータルに表示する
- プラグインは**本体の SDK（`src/care-sdk`）経由でしかデータを読み書きできない**。同意、暗号化、監査ログ、危機検知は SDK が担うので、プラグインの作者は気にしなくてよい

```
tools/kokoro-log/
  manifest.ts      # 名前、説明、アイコン、各項目（id, ラベル, 型, 危機検知の対象にするか）
  schema.ts        # 記録 1 件の型（zod）
  Entry.tsx        # 相談者が記録する画面
  History.tsx      # 相談者が自分の記録を振り返る画面
  AdminView.tsx    # 共有されている場合に、管理者が見る画面
  README.md
```

- **SDK の API（案）**

  | 関数 | 内容 |
  |---|---|
  | `saveEntry(toolId, data)` | 検証し、危機検知をして、暗号化して保存する。危機を検知した場合は `{ crisis: true, resources }` を返す |
  | `listMyEntries(toolId)` | 相談者が自分の記録を取得する |
  | `getConsent(toolId)` / `setConsent(toolId, shared)` | 同意を取得・変更する（変更は履歴に残る） |
  | `listSharedEntries(toolId, subjectId)` | 管理者向け。同意がなければ空を返す。呼ぶたびに監査ログに残す |
  | `<CrisisResources />` | 相談窓口を表示する共通コンポーネント |

### 決定事項（Claude Code でツールを作るためのテンプレート）
- `tools/_template/`: 最小構成のプラグインのひな形
- `.claude/skills/new-care-tool/`: 「〇〇のツールを作りたい」と伝えると、ひな形をコピーして manifest、schema、画面を生成する skill
- `tools/CLAUDE.md`: ツールを作るときのルール
  - SDK 以外で DB に触らない
  - 外部への送信をしない
  - 診断的な表現をしない
  - 自由記述の項目は危機検知の対象にする
- `pnpm tools:check`: 規約違反（DB への直接アクセス、`fetch` の使用など）を検出するスクリプト。公開前のチェックに使う

## 11. デモの台本

0. **（年忌法要の問い合わせ）** 住職「山田さんから、お父さんの七回忌を 3 月にやりたいと連絡があった」
   - 故人を特定する（候補が複数あれば確認を求める）→ 没年から**七回忌が本当にその年にあたるか**を検証する → 祥月命日より後の日になっていないかを確認する → 同じ年に年忌を迎える家族がいれば併修を提案する
   - 担当者（住職、副住職、執事長）の空きと、本堂の空き（前撮りや茶会の予約と重ならないこと）から、候補の日時を出す
   - 住職「3/15 の 10 時、住職の担当で」→ プレビュー → 了承 → 法要、担当者の予定、本堂の予約がまとめて登録される → 管理画面のカレンダーに表示される
1. 住職「来月、年忌を迎えるお家を教えて」→ 回忌ごとに一覧が返る
2. 住職「田中家に三回忌のご案内をしたと記録しておいて」→ プレビュー → 了承 → 対応記録が追加される
3. 住職「お会式の参加確認フォームを作って。人数と、お斎が必要かも聞いて。檀家さんにも一般の方にも」→ `both` モードのフォームとリンクができる → スマートフォンで、個別リンク（簡易版）と共通リンク（全項目版）からそれぞれ回答する → 「今の参加人数は？」で集計が返る
4. 外部の人がスマートフォンから「12/6 午前に本堂で前撮り」を申請する → 住職「承認待ちの予約はある？」→ 法要と重ならないことを確かめてから承認する
5. 相談者がスマートフォンから匿名で「こころの記録」をつける → 共有に同意する → 管理画面に表示される。危機的な言葉を書くと、本人には相談窓口が表示され、管理画面にはアラートが出る → 同意を撤回すると見えなくなる。最後に Claude Desktop で聞いても、ケアのデータは参照できないことを見せる
6. お坊さんが Claude Code で「写経の記録ツールを作りたい」と伝える → skill でプラグインが生成される → `tools:check` が通る → ケアのポータルに表示されて、そのまま使える
7. **（檀家ポータル）** 施主の山田さんがスマートフォンでログインする → 家系図と、家の法要の予定（「来年 父 七回忌」の目安）を見る → そのまま法要の申し込みフォームから七回忌を申し込む → 住職が Claude Desktop で「新しい法要の申し込みはある？」と聞く → 場面 0 と同じ流れで検証し、日時を確定させる → 施主のポータルに確定した予定が表示される。家族（息子）は施主から閲覧を許可されているので、同じ予定が見える。お会式にも申し込める
   - ※ 場面 0（電話での受付）と場面 7（ポータルからの申し込み）は、デモの時間に合わせてどちらかを主にする
