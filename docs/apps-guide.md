# お寺のアプリを Claude Code で作る手順書

> 住職（またはお寺の人）が「こんな機能がほしい」と思ったときに、Claude Code と一緒に「お寺のアプリ」を作るための手順書。
> 仕様は [spec.md](spec.md) §7、Claude Code が守るルールは [apps/CLAUDE.md](../apps/CLAUDE.md)。

## 1. お寺のアプリとは

台帳や法要、カレンダーなどの基本機能とは別に、お寺ごとに欲しい小さな機能を足すしくみ。
利用者はスマートフォンで `/apps` を開き、名前やメールアドレスなしで、ニックネームだけで使える。

例: 日記・ノート、占い・おみくじ、写経の記録、お寺独自の形式のアンケート
（行事の申し込みやふつうのアンケートは、まず本体の「行事・アンケート」を使う）

アプリを作る人が考えるのは、**画面と、保存するものの形だけ**。次のことは基盤が受け持つ。

| 基盤が受け持つこと | 内容 |
|---|---|
| 匿名の利用 | ニックネームだけで始められる。ID は端末の cookie にだけ保存する |
| 保存と暗号化 | アプリが `useAppStorage` で保存した文書を、暗号化して保存する。本人だけが読める |
| お寺との共有 | `sharing: true` のアプリでは、利用者がアプリごとに「お寺と共有する / しない」を選べる。共有のボタンや文言はアプリが自由に作れる（`useAppSharing`）。どのアプリでも、画面の上の帯に今の状態と基盤の共有の設定へのリンクが出る。やめるとすぐにお寺から見えなくなる。変更の履歴と監査ログを残す |
| スタッフの閲覧 | 共有された文書を、管理画面（`/admin/apps`）でアプリの Admin.tsx を使って表示する（読むだけ）。開くたびに監査ログに残す |
| AI | `ai` を宣言したアプリだけ、利用者が同意したときに、アプリが渡した入力を基盤のサーバーから Claude に送る（キーと費用は運用者。利用者ごとと全体の回数、アプリごとの月の費用に上限）。送った内容は保存もログもしない。管理画面（`/admin/apps`）で、今月の回数と費用を見られる |
| 素材、全画面、ホーム画面 | `assets/` の画像や音を配信する（SVG は不可）。全画面のアプリには右上の小さなボタンだけを出す。アプリごとの Web App Manifest を出す |
| MCP からの保護 | 利用者のデータは、MCP（Claude Desktop）からは一切読めない |

## 2. しくみ

```
apps/<app-id>/            ← アプリを作る人が書く
  manifest.ts             名前、説明、アイコン、共有、画面の出し方、ホーム画面、保存の上限、AI
  App.tsx                 利用者の画面（useAppStorage で保存する）
  Admin.tsx               スタッフの画面（共有を使うときだけ）
  ai.ts                   AI の仕事の宣言（AI を使うときだけ。サーバーで読み込まれる）
  assets/                 素材（SVG は不可）
  README.md

npm run apps:gen          → src/apps-sdk/*.generated.ts（アプリの一覧。自動生成）

src/apps-sdk/             ← アプリが import できる唯一の窓口（useAppStorage、useAppSharing、useAppAI、useAppAssets と型）
                            ai-server.ts / ai-schema.ts は、AI の呼び出しの共通の処理（本体とキットで同じ）
src/domain/apps/          ← 基盤: 保存、暗号化、共有の履歴、監査ログ
src/app/apps/             ← 利用者の画面（/apps）と、文書の読み書きの API（/apps/api/<app-id>/docs）
src/app/admin/apps/       ← スタッフの画面（/admin/apps）
```

- アプリの画面（App.tsx）は、利用者のブラウザで動く React。`useAppStorage` が基盤の API を呼び、基盤が cookie の利用者とアプリの ID を確かめてから保存する。アプリのコードからは、ほかの人やほかのアプリのデータに触れない
- ただし、アプリのコードはお寺のサイトの中で動くので、わざとルールを破るコードは防げない。`npm run apps:check` は、うっかりした違反（`fetch` や DB の import など）を見つけるためのもの。**公開の前に、必ず人がアプリのコードを読む**

## 3. 作り方（Claude Code）

### 3-1. 準備
```sh
docker compose up -d
cp .env.example .env      # はじめてのときだけ
npm install
npm run db:reset
```

### 3-2. Claude Code に頼む
このリポジトリで Claude Code を起動し、作りたいものを伝える。skill（`.claude/skills/new-temple-app/`）が呼ばれ、ひな形から作ってくれる。

頼み方の例:
- 「毎日ひとこと書ける日記のアプリを作りたい。書いた日記を、本人が希望したら住職に見せられるように」
- 「今日の運勢を引けるおみくじのアプリを作って。大吉から凶まで 7 種類で、引いた結果の履歴が残るように」
- 「写経をした日と、写した経典、心に残った言葉を記録するアプリがほしい」

Claude Code は、足りないこと（保存するもの、共有を使うか、名前とアイコン）をまとめて聞いてから作る。
基盤にない能力（お寺に送る、お寺が内容を編集する、檀家としてログインする）が必要なものは、今はできないことと、できる範囲の案を返す。

### 3-3. 確かめる
```sh
npm run apps:check    # 規約違反が 0 件であること
npm run dev           # 起動中なら、かわりに npm run apps:gen
```
1. `http://localhost:3000/apps` を開き、ニックネームで始める
2. アプリを選び、作る・直す・消すを試す。ページを読み直しても残っていることを確かめる
3. 共有を使うアプリなら、アプリの共有のボタン（または画面の上の「共有の設定」）で共有する。帯の表示が「お寺と共有中」に変わることを確かめる
4. 管理画面（`http://localhost:3000/admin/apps`。`jushoku@example.com` / `password`）で、共有した利用者とデータが見えることを確かめる
5. `/apps` に戻って共有をやめ、管理画面から見えなくなることを確かめる

### 3-4. 公開の前のチェックリスト
- [ ] `npm run apps:check`、`npm run typecheck`、`npm run lint` が通る
- [ ] 人がアプリのコードを読み、データの持ち出しや外部への送信をしていないことを確かめた（`apps:check` は悪意のある書き方までは見抜けない）
- [ ] スマートフォンの画面で、文字が読みやすく、ボタンが押しやすい
- [ ] 消す操作の前に確認が出る
- [ ] 共有を使うアプリでは、共有をオンにする前に、何が共有されるか（お寺の方が読めるようになる、これまでの分も含む、読むだけ、いつでもやめられる）が説明されている。画面を開いただけや、ほかの操作に紛れて共有されない
- [ ] 共有を使うアプリでは、Admin.tsx に、利用者が保存した内容だけが表示される
- [ ] README に目的、文書の形、画面の説明が書いてある

公開は、アプリのディレクトリをリポジトリに入れて、`npm run apps:gen` で一覧に載せること（下書きの状態はまだない）。

### 3-5. お寺さんに作ってもらう（開発キット）
本体を渡さずに、お寺さんにアプリを作ってもらうときは、開発キットを渡す。

```sh
npm run kit:build     # dist/temple-app-kit.zip ができる
```

キットには、試す画面（本体に近い見た目。保存先はブラウザの中。AI は試す画面のサーバーが本体と同じ処理で Claude を呼ぶ。キーはお寺さんの `.env`）、本体と同じ API の SDK、`apps:check`、ひな形、Claude Code の決まりと skill、お寺さん向けの `README.md` が入っている。`.env` は zip に入らない。

送られてきたアプリ（`apps/<app-id>/` の zip）を組み込むとき:
1. zip を展開し、`apps/<app-id>/` に置く（同じ ID のアプリがないことを確かめる）
2. **コードを読む**: データの持ち出しや外部への送信がないか、共有をオンにする前に説明があるか、Admin.tsx に保存した内容だけを出しているか。AI を使うアプリでは、`ai.ts` の指示（利用者の入力を混ぜていないか、不適切な指示がないか）、`ai.sends` と `ai.purpose` が実際に送るものと合っているか、モデルと 1 日の回数（費用）、AI が失敗したときにアプリが止まらないか。素材の中身（大きさ、権利）
   - AI の費用の上限を決める: アプリごとの月の上限は `APPS_AI_MONTHLY_BUDGET_USD`（初期値 10 ドル）、アプリごとに変えるときは `APPS_AI_BUDGETS_USD`（JSON）。キーは `ANTHROPIC_API_KEY`（サーバーの環境変数）
3. `npm run apps:gen`、`npm run apps:check`、`npm run typecheck`、`npm run lint`
4. `npm run dev` で、上の「3-3. 確かめる」を本体で試す（日時の表示など、試す画面と違うところがないか）
5. コミットする

## 4. `npm run apps:check` が見ること

- 必要なファイル（manifest.ts、App.tsx、README.md。`sharing: true` なら Admin.tsx）がそろっている
- manifest の `id` がディレクトリの名前と同じ。`name`、`description`、`icon`、`sharing` が書いてある。`display`、`pwa`（色、512×512 の PNG のアイコン）、`storage.maxDocs`、`ai`（purpose、sends、モデル、1 日の回数）の値の範囲
- import が `@/apps-sdk`、`react`、`zod`、自分のディレクトリの中（と `*.module.css`）だけ。`ai.ts` は `zod` と `@/apps-sdk` だけ
- `fetch` などの外部への送信、外部の URL（SVG の名前空間は除く）、`process.env`、`localStorage` や cookie、`eval`、`"use server"`、`dangerouslySetInnerHTML` を使っていない
- `ai.ts` の仕事の形（指示、返事の形が JSON Schema にできるか、入力の上限）。manifest の `ai` と `ai.ts`、`useAppAI` の使い方が合っているか
- 素材の種類（SVG は不可）と大きさ。CSS は `*.module.css` だけで、`:global`、`@import`、外部の URL を使っていない
- アプリの一覧（`*.generated.ts`）が最新

## 5. まだできないこと（ハッカソン後）

詳しくは spec.md §7 の「検討して採らなかった案」と「未決事項」。
- 利用者が 1 件ずつお寺に送る（申し込み、回答、奉納など）
- スタッフが管理画面で、アプリの内容（おみくじの文言、設問など）を編集する（今は内容をアプリのコードに書く）
- 檀家ポータルのアカウントで使う
- オフライン、プッシュ通知、AI の画像生成、課金、大きなデータの分けた読み込み
- 引き継ぎコード（iPhone で、Safari とホーム画面のアプリとで利用者が分かれるのをつなぐ）は準備中（docs/tasks/08-apps.md）
- 下書きの状態（スタッフだけが試せる）、アプリの審査
- アプリの隔離（iframe の sandbox）
